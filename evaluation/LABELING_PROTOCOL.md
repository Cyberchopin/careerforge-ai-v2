# Labeling protocol v1 — frozen before scoring

Date: 2026-09-17. Applies to the synthetic dataset generated by `dataset/build-dataset.mjs` with seed `20260916`. This protocol describes the controlled labels already authored with the source records; it does not imply that an outside reviewer has confirmed them. No CareerForge or baseline output was used to set those labels.

## Unit and evidence boundary

The unit is one atomic `candidate_claim`, evaluated against **only** the `resume_evidence` array of its own `resume_id`. Do not use world knowledge, other resumes, the model's explanation, linked sites, or the candidate's asserted wording as independent evidence. Split by whole resume, not claim. Do not view `generated/test.jsonl` during prompt/rule tuning; its committed presence is reproducibility, not a technical access lock.

## Three mutually exclusive labels

- `supported`: every material element of the claim (action, ownership, tool, metric, scope, credential, and outcome where stated) is directly entailed by supplied evidence. Harmless paraphrase is allowed; a stronger implication is not.
- `partial`: at least one material element is directly supported, but another is overstated, contradicted, or absent. Examples: 20 measured units become 30; implementation ownership becomes sole strategy-through-delivery leadership. Partial does **not** count as verified.
- `fabricated`: no supplied evidence supports the claim's central event, role, credential, technology, or outcome. Generic word overlap does not turn fabrication into partial support. Examples: Kubernetes production deployment where no deployment is recorded; a six-person management role and award with no corresponding record.

For binary unsupported-claim detection, `unsupported = partial OR fabricated`. Report the three-class confusion matrix as well; never silently redefine unsupported to mean only fabrication. If a claim bundles supported and entirely ungrounded events, label `partial` and flag the bundling in failure analysis. If genuinely ambiguous, mark for adjudication before examining system predictions; do not force the label to match a model output.

## Blind process and lock

1. Controlled facts, claims, `ground_truth`, and rationales are authored together in the dataset builder. The manifest fixes file SHA-256 hashes and the resume-level split.
2. A label reviewer, if recruited, receives evidence and claims **without** CareerForge/baseline outputs, system names, or predicted citations. The reviewer records label, cited source IDs, reason, and ambiguity flag before any model predictions are unblinded.
3. A second reviewer independently labels the same cases if available. Disagreements are adjudicated against the written rules, with original labels, reasons, and adjudication preserved. Do not overwrite the original annotation silently.
4. Any label correction after viewing a prediction is a protocol deviation; log it with cause and report sensitivity both with and without the corrected case.
5. The six-resume test split remains unopened for tuning. Model, prompt, schema, gate versions, and metric code must be frozen before its first scored run. A failed or inconvenient test result does not permit prompt revision and re-running as if still held out.

External blind review is **not complete**. Reviewer invitation/confirmation is a separate human dependency; no independent inter-rater agreement is claimed.
